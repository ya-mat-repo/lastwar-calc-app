# Last War ツール集

Last War のためのツールをまとめたアプリです。トップページ（目次）から各ツールを開きます。

| ページ | URL | 内容 |
| --- | --- | --- |
| トップ | `#/` | ツールの目次 |
| ポイント計算機 | `#/calc` | 下記 |
| 最安イベント早見 | `#/shop` | 準備中 |

## ポイント計算機

現在値を入力すると、曜日ごとの獲得値の組み合わせで目標値 **7,200,000** ちょうどに到達するパターンを表示します。

目標値はヘッダーの「目標値」をタップして変更できます（初期値 7,200,000）。
入力できるのは 1〜99,999,999 の整数で、それ以外のあいだは計算を止めて入力を促します。
変更した値はブラウザに保存され、`↺` で初期値に戻せます（初期値のままなら保存しません）。

> **仕様は [SPEC.md](./SPEC.md) を参照。** 振る舞いの定義・不変条件・実装側で判断した点をまとめてあり、
> コードレビューの判断基準として使う。原典の要件は `アプリ仕様書.md`。

## 技術構成

- React 18 + Vite + **TypeScript**（フロント完結・サーバー不要）
- 依存ライブラリなしの自作ソルバー（`src/solver.ts`）
- テストは Vitest
- Vercel に静的サイトとしてデプロイ

### ファイル構成

| ファイル | 役割 |
| --- | --- |
| `src/data.ts` | 曜日ごとの獲得値（仕様書からの転記）とグループ（加速・結束）の定義。`Day` / `DayKey` / `ItemGroup` 型 |
| `src/solver.ts` | 組み合わせソルバー。`PreparedDay` / `Pattern` / `SolveResult` 型 |
| `src/state.ts` | 画面状態の純粋ロジック。`EditableDay` / `PriorityMap` 型 |
| `src/App.tsx` | UI |

## 開発

```bash
npm install

npm run build      # dist/ を生成
npm run preview
npm test           # テストを1回実行
npm run test:watch # 変更を監視して再実行
```

## テスト

テストランナーは **Vitest**（`vite.config.ts` を共有するため設定ファイル不要）。

| ファイル | 対象 | 実行環境 |
| --- | --- | --- |
| `src/solver.test.ts` | 組み合わせソルバー（前処理・探索・並び順・超過フォールバック） | node |
| `src/state.test.ts` | 画面状態の純粋ロジック（入力パース・編集判定・優先アイテム操作） | node |
| `src/App.test.tsx` | UI の配線（入力→計算→表示、タブ、編集、優先指定、a11y） | jsdom |

ロジックの大半は純粋関数なので node 環境で速く回す。
UI テストだけファイル先頭の `// @vitest-environment jsdom` で jsdom に切り替えており、
グローバル設定は変えていない（純粋ロジックのテストは jsdom の起動コストを払わない）。

UI テストは **Testing Library**（`@testing-library/react` + `@testing-library/dom` + `jsdom`、
いずれも devDependencies）。ランタイム依存は React のみのまま。

### 総当たり参照実装との突き合わせ

ソルバーは拡張ユークリッド互除法で最小回数解を「計算」する。
テスト側には全パターンを「数え上げる」素朴な実装（`bruteSubsetMin` / `bruteExpected`）を置き、
小さな入力で両者の結果が完全に一致することを確認している。検証しているのは以下。

- 上位20件の**アイテムの組み合わせと並び順**が一致すること
- 各組み合わせの**最小合計回数**が一致すること（内訳は同点解がありうるので合計が一致することを確認）
- 優先指定ありの場合の**スコアと並び順**が一致すること
- ぴったり作れないときの**超過値が本当に最小**であること（不足額を全数走査）

## 獲得値の編集

結果一覧の上の「◯曜日の獲得値」を開くと、行動名・値の変更、行の追加・削除ができます。
人によって値が前後する場合はここで調整してください。

- 変更は**メモリ上のみ**。リロードすると仕様書どおりの初期値に戻ります。
- 編集した曜日はタブに ● が付き、見出しに「編集済み」バッジが出ます。
- 「初期値に戻す」でその曜日だけ元に戻せます。
- 空欄・0・負数・不正な値の行は計算対象から自動的に除外されます（入力欄は赤枠で表示）。
- 小数は 4 桁まで対応（5桁以上は 4 桁に丸めて計算します）。
  同じ値の行は 1 つの選択肢としてまとめられます。
- **獲得値に小数を入れるときは注意**してください。ゲームは1回の使用ごとに端数を切り上げて
  整数でポイントを付与するので、`.5` の値を n 回使うパターンは実際には n/2 ずれます
  （例: チップ宝箱(R) を 2,812.5 としていたとき、28回で +14 ずれた）。
  初期値に小数の獲得値はありません。
- **`チップ宝箱(R)開封`（2,813）と `チップ宝箱(SR)開封`（14,063）は必ず1個ずつ使ってください。**
  まとめて使うと合計に対して1回しか切り上げられず、結果が変わります
  （チップ宝箱(R) 10個: 1個ずつなら 28,130、まとめて使うと 28,125）。
  アプリは1個ずつ使う前提の値で計算していて、月曜の獲得値パネルと、
  該当アイテムを2回以上使う結果カードの行に注意書きを出します。

## グループ（加速・結束）

「基準値 1 つ × 倍率」で複数サイズをまとめて扱う枠です。編集パネルの上部に出ます。

| 曜日 | グループ | 種別 | 基準 | サイズ |
| --- | --- | --- | --- | --- |
| 月 | UR / SSR / SR英雄かけら | 結束 | 1枚 = 25000 / 8750 / 2500 | 10枚 / 20枚 / 30枚 / 40枚 / 50枚 |
| 火 | 建造 | 加速 | 1分 = 150 | 1分 / 5分 / 1時間 / 3時間 / 8時間 |
| 火 | 兵装素材 | 結束 | 1個 = 2.5 | 10k個 / 20k個 / 30k個 / 40k個 / 50k個 |
| 火 | 兵装コア | 結束 | 1個 = 6250 | 10個 / 20個 / 30個 / 40個 / 50個 / 60個 / 70個 |
| 水 | 科学研究 | 加速 | 1分 = 150 | 加速の5サイズ |
| 木 | 覚醒 / 専用武装 / UR / SSR / SR のかけら | 結束 | 1枚 = 25000〜2500 | かけらの5サイズ |
| 金 | 建造・科学研究・訓練 | 加速 | 1分 = 150 | 加速の5サイズ |

- **編集できるのは「基準 ◯◯ = 」だけ**です。他のサイズは倍率を掛けて自動計算されます
  （1時間 = 1分 × 60、10k個 = 1個 × 10,000）。各行に計算式が出るので、どこを直せばよいか分かります。
- チェックを外すと、そのサイズは候補から除外されます。
  持っていない加速サイズや使わない結束単位を外しておくと、実際に使える組み合わせだけが出ます。
- **結束は結束単位でしか使えない**ので、1個ぶん・1枚ぶんそのものは候補に入りません。
  「基準 1個 = 」「基準 1枚 = 」は各単位の値を出すための係数です。
- 同じ値になるものは1つの候補にまとまります
  （兵装素材50k個 と 兵装コア20個 はどちらも 125,000、木曜の 覚醒 / 専用武装 / UR英雄 は3種とも同じ値）。
- 金曜の建造・科学研究・訓練は 3 つとも同じ値なので、1 グループにまとめています。
- 基準値の変更もチェックの状態も、獲得値の編集と同じくリロードで初期状態に戻ります。

## 優先して使うアイテム

獲得値の下の「優先して使うアイテム」を開くと、その曜日のアイテムがチップで並びます。
タップした順に ①〜⑤ が付き（最大5件）、もう一度タップで解除・後ろの順位が繰り上がります。

- チップは**上の獲得値パネルと同じ並び**なので、目当てのアイテムを同じ位置で探せます。
- **絞り込みではなく並び替え**。優先外のパターンも下に残るので比較できます。
- 並び順は「優先スコアが高い順 → 種類数が少ない順 → 合計回数が少ない順」。
- 優先スコア = パターンが含む優先アイテムの重みの合計（①=5, ②=4, ③=3, ④=2, ⑤=1）。
  多く含むほど上位、同点なら従来どおりの順序になります。
- 結果カードの該当行にも ①②③ が表示されます。
- 選択は曜日ごとに独立。値を編集・削除して該当アイテムが消えると自動的に外れます。

## 計算ロジック

`src/solver.ts`

1. 差分 `D = 7,200,000 − 現在値` を求める。
2. 値の小数桁数（最大4桁）から倍率を決めて整数化し、さらに全体の GCD で割って探索空間を縮小する。
   例: 火曜は全値が 150 の倍数なので GCD 150 で除算（＝実質 150 刻み）。小数の値があれば先に 10^n 倍する。
3. 使う値の**種類数** k = 1, 2, 3 について、値の組み合わせごとに
   `v1·c1 + v2·c2 + v3·c3 = D`（各 c ≥ 1）の**合計回数が最小になる解**を
   拡張ユークリッド互除法で 1 件求める。
4. 「優先スコアが高い順 → 種類数が少ない順 → 合計回数が少ない順」で並べ、上位 20 件を返す。
   優先指定が無いときは 20 件揃った時点で探索を打ち切るが、指定があるときは
   上位20件の顔ぶれが変わるため全組み合わせを走査する（金曜・12種で最大 84ms）。
5. ぴったり作れない場合は、到達可能な値を 1 単位ずつ上げながら探索し、
   **目標値を超える中で最も近い到達値**のパターンを表示する。
   走査の上限は「1 種類だけで作れる最小の超過値」（必ず到達可能）としているため、
   値を編集して刻みが極端に粗くなっても必ず解が返る。

### 仕様上の解釈・制限

- 「組み合わせる値の数が少ないものを優先」は**使う値の種類数**と解釈。
  同種類数のときは合計回数が少ない順。
- 木曜の 25000（覚醒かけら／専用武装のかけら／UR英雄かけら）のように
  同じ値の行動は 1 つの選択肢にまとめ、ラベルを併記する。
- 探索は種類数 3 までを対象（実運用の差分では 2 種類までで十分な候補数が出るため）。

## 型安全について

`tsconfig.json` は `strict` に加えて以下を有効にしている。

- `noUnusedLocals` / `noUnusedParameters` — 消し忘れの検出
- `noImplicitReturns` — `switch` の分岐漏れ（`SolveStatus` を増やしたときの書き忘れ）を検出
- `noFallthroughCasesInSwitch`
- `exactOptionalPropertyTypes`
- `verbatimModuleSyntax` — 型のみの import は `import type` を強制

ソルバーの戻り値（`SolveResult` / `Pattern` / `Option`）は全て `readonly` にしてあり、
計算結果を UI 側でうっかり書き換えられないようにしている。

`noUncheckedIndexedAccess` は**あえて無効**。ソルバーは境界が保証された数値ループで
配列を大量に添字アクセスするため、有効にすると意味のない `!` が20箇所以上増えて
かえって本当に危険な箇所が埋もれる。配列外アクセスの安全性はテスト側で担保している。
